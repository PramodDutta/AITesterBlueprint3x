What is LangChain?

LangChain is a framework for building applications powered by large language models. It gives you the building blocks (models, prompts, tools, memory, retrieval) and a single create_agent() function that wires them into an agent.

A LangChain agent is an LLM-powered system that can understand user input, reason, and generate responses. Give it tools and it can also take action: run a calculation, call an API, fetch a page, generate test cases in a fixed format.

Agent = Model + System prompt + Tools + a loop. The model reads the messages, decides whether to answer or call a tool, and repeats until the task is done. Everything in this guide is a variation of that one idea.

LangChain vs LangGraph vs LangSmith

The LangChain ecosystem: purpose, features and differences. This course covers the first column.

LangChain

Build LLM applications easily

A framework for developing LLM-powered applications. It provides the building blocks to chain components together and create end-to-end apps.

Key capabilities

  • Prompt templates and few-shot examples
  • LLM integrations (OpenAI, Anthropic, Gemini, Ollama)
  • Chains: LLMChain, SequenceChain, RouterChain
  • Agents: tool calling, MRKL, ReAct agents
  • Memory: conversation buffer, summary, vector store
  • Retrieval: document loaders, text splitters, vector stores
  • Tools and functions: integrate external tools and APIs
  • Easy to start with pre-built components

Best for

Quickly building LLM apps, chatbots, RAG pipelines and AI agents with minimal orchestration complexity.

Example use cases

  • Chatbots
  • RAG apps
  • Tool-using agents
  • Q&A over documents

LangGraph

Build stateful, multi-agent workflows

Builds on LangChain to help you create stateful, cyclic and deterministic workflows (graphs) for complex multi-step AI applications.

Key capabilities

  • Graph-based workflow orchestration (nodes and edges)
  • Stateful execution with persistent memory
  • Cycles, loops, branching, conditional routing
  • Human-in-the-loop and interrupts
  • Multi-agent collaboration patterns
  • Durable execution and checkpointing
  • Streaming and real-time updates
  • Works with LangChain components inside nodes

Best for

Complex, production-ready AI workflows that need control, state management, branching and cycles.

Example use cases

  • Multi-step AI workflows
  • Multi-agent systems
  • Human-in-the-loop
  • Long-running stateful apps

LangSmith

Debug, test, evaluate and monitor

A developer platform for observability and evaluation of LLM applications. It helps you debug, test, evaluate and monitor your chains and agents.

Key capabilities

  • Tracing: see every LLM call, chain, tool and sub-step
  • Debugging: inspect inputs, outputs, prompts, errors
  • Evaluation: test datasets, expected outputs, scoring
  • Experimentation: compare prompts, models, strategies
  • Monitoring: production logs, latency, tokens, cost
  • Datasets: manage test sets and golden datasets
  • Collaboration: share traces, feedback, annotations
  • Integrates with LangChain and LangGraph

Best for

Observability, debugging, evaluation and monitoring of LLM applications in development and production.

Example use cases

  • Debug failing agents
  • Evaluate outputs
  • Compare models and prompts
  • Monitor production

Use LangChain when

  • You want to quickly build LLM apps, chains, RAG pipelines or simple agents.
  • Great for prototypes and straightforward use cases.

Use LangGraph when

  • Your application has multiple steps, decisions, loops or human approvals, or needs robust stateful workflows.
  • Great for multi-agent systems and enterprise workflows.

Use LangSmith when

  • Throughout the lifecycle: debug, evaluate, test and monitor your LLM apps in development and production.
  • Essential for quality, reliability and iteration.

Setup: Python and .env

  2. Install LangChain and the providers you will use

02

invoke vs stream

Two ways to get an answer, and the system + user message pattern that makes agents behave.

At a glance

invoke

  • Get the complete response at once
  • Simple and easy
  • Best for scripts and batch processing
VS

stream

  • Get the response token by token
  • Feels faster (real-time)
  • Best for chat UIs and live tools

A system message sets the behaviour and expertise of the agent. The user message is the actual question. This pair is the foundation of every good agent.

Run: python src/chapters/003_Hello_Gemini_Steam.py

Output
Agent Response:
Automation testing is the process of using tools and scripts to test software
applications automatically. It helps find bugs faster, saves time, and improves
software quality.

Streaming Response:
Smoke testing is a quick check that the most important features of a build
work... (appears word by word)
Featureinvokestream
Response styleFull response at onceToken by token
Use caseScripts, batch processingChat UIs, live demos
Speed perceptionWaits until the endFeels faster (typing effect)
Memory usageLower for short responsesSlightly higher
ComplexityVery simpleSlightly more code

In automation testing agents we often use both: stream for developer-facing tools where someone is watching, invoke for backend workflows such as CI jobs.

Key takeaways

  • invoke() returns the complete response (most common for starters)
  • stream() with stream_mode="messages" yields tokens in real time
  • Always use a system message to define the agent's role
  • Proper message structure (role + content) is the foundation of good agents
  • These two methods cover 95% of LangChain agent implementations

System prompts: giving your agent a personality and instructions

A system prompt is a job description you hand the agent before the conversation starts.

At a glance

User message

  • What the user asks
  • The actual question or request
  • Changes every time
VS

System prompt

  • Defines who the agent is
  • Sets behaviour, tone and rules
  • Stays constant
  • Huge impact on response quality

It tells the agent who it is, how it should behave, what tone to use and what rules to follow. Think of hiring: system prompt = job description, user message = task given, agent response = work delivered.

04

Parallel agent calls: running multiple queries efficiently

Work smarter, not slower. asyncio.gather() is Python's Promise.all().

At a glance

Sequential calls

  • One by one execution
  • Takes more time
  • Blocks the next call
  • Not efficient for batch work
VS

Parallel calls (asyncio.gather)

  • All at the same time
  • Much faster
  • Independent execution
  • Perfect for batch processing

Run: python src/chapters/005_Agent_Parallel_Vs_Sequential.py

Output
1. Smoke Testing
Smoke testing is a type of testing to verify that the basic functionality of an
application works as expected. It is done at the build level to ensure stability.
----------------------------------------------------------------------
2. Sanity Testing
Sanity testing is performed to check that recent changes or bug fixes are working
as expected. It is a narrower and more focused type of testing.
----------------------------------------------------------------------
3. Regression Testing
...
Finished 3 calls in 2.1s

Shortcut: agent.batch([input1, input2, input3]) runs a list of inputs in parallel with one synchronous call. asyncio.gather is the pattern to know when you mix agents with other async work (Playwright, HTTP calls, databases).

Key concepts

  • asyncio.gather() runs multiple coroutines in parallel, like Promise.all()
  • Each agent.ainvoke() is independent but uses the same agent config
  • The system prompt is shared across all calls
  • Results arrive in the order of the original list, so zip(questions, results) lines them up

Real testing use cases: generate test cases for multiple user stories at once, explain multiple testing concepts, analyse multiple bugs in parallel.

Exercises

  1. Add 3 more testing concepts to the questions list.
  2. Run 8 to 10 questions at once.
  3. Measure the time with asyncio.gather and again with a plain for loop calling agent.invoke(). Note the difference.

Creating your first tool and agent

Give your agent a tool and watch it do real work instead of guessing.

At a glance

Without tools

  • Agent can only reply using its knowledge
  • Cannot perform calculations or external tasks
  • Limited to text responses
VS

With tools

  • Agent can call tools to do real work
  • Gets accurate and dynamic results
  • Much more powerful and useful

A tool = function + metadata + input schema. In Python the @tool decorator builds all three from one function:

function body

The implementation. What runs when the agent calls the tool.

name + docstring

The metadata. Function name = tool name, docstring = description that tells the agent when to use it.

type hints

The schema. expression: str is what Zod did in TypeScript: it defines the expected input shape.

  • Tools extend agent capabilities beyond LLM knowledge
  • A tool = function + metadata + input schema, all from @tool

Final project: a Playwright agent that runs your test

How it works

shared state

All tools read the same _page. Launch creates it, close clears it, every other tool checks it exists before acting.

async everywhere

Playwright's async API, async def tools and agent.ainvoke(). Mixing the sync API with the agent's thread pool breaks, so keep it all async.

the loop

The agent calls a tool, reads the string it returns, decides the next call. Eight steps in the task become eight tool calls plus a report.

Where this fits in real testing: agents are great for exploratory checks, smoke runs and "does this flow still work?" questions. For your regression suite keep scripted tests: they are cheaper, faster and deterministic. The next step is to combine both, for example generate a test with the agent, then save it as a normal pytest-playwright test.

Key takeaways

  • Tools can drive anything, including a real browser
  • Return short, clear strings from tools: they are the agent's eyes
  • Rules in the system prompt (launch first, screenshot before close, report at the end) make multi-step runs reliable
  • Use the async Playwright API with agent.ainvoke()
  • Read the message history to see every step the agent took

What actually broke when we ran this

Every code block on this page was executed, not just written. These are the failures that cost real time, in the order you are most likely to hit them.

1. A Gemini key that starts with AQ. is not an API key

A real Gemini key starts with AIza. A value starting with AQ. is a short-lived OAuth access token: it works for about an hour, then every call fails with a message that never mentions expiry.

Check before you debug anything else: python -c "import os;print(os.getenv('GOOGLE_API_KEY','')[:4])" must print AIza.

2. The env var name the SDK looks for is not always the one in your .env

ChatDeepSeek auto-reads DEEPSEEK_API_KEY. If your file calls it DEEPSEEK_API, the key is silently ignored and you get a 401 that says nothing about variable names. Pass it explicitly, or rename the variable.

3. load_dotenv() has to run before os.getenv, not near it

This orders wrong and fails with a confusing error three frames inside LangChain, because os.getenv returned None long before load_dotenv() ran:

Prefer os.environ["LLM_MODEL"] over os.getenv(...) for required values: a missing key then fails immediately with a KeyError naming the variable, instead of passing None down the stack.

4. Gemini returns content blocks, not a string

Printing message.content on a Gemini reply gives you this, signature blob and all:

Use message.text instead. In langchain-core 1.x it is a property that concatenates the text blocks and drops the rest. (In 0.3 it was a method, message.text().) Do not hand-roll a block parser, the library already has one.

5. The same tools, two models, two very different agents

Chapters 09 and 10 are the same agent, the same 32 tools and the same system prompt. Only the model differs. The task said "1. Launch the browser" as its first step:

ModelWhat it did
openai/gpt-oss-120b (Groq) Called navigate_to before launch_browser, got the error string back, launched, snapshotted a blank page, then gave up after 3 steps.
deepseek-chat Followed the order, then went further than asked: verified the post-login URL and title, asserted text=Products was visible, screenshotted, closed cleanly. PASSED.

That is the lesson of the whole chapter: tool-call discipline is a property of the model, not of your prompt. It is also exactly why every tool returns an error string instead of raising, which is what made Groq's misstep recoverable rather than fatal.

6. Do not eval() what a model wrote

The obvious one-line calculator tool is eval(expression). That is arbitrary code execution driven by text a language model produced. 006_Tool.py walks the parsed expression instead, so __import__('os').system(...) is rejected as "only arithmetic is allowed" rather than executed.
